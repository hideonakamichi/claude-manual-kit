# CLAUDE.md — Instagram カルーセル作成システム 共通方針

このファイルは、**オーケストレーター**（Claude Code のメインセッション）が毎回読み込む共通ルール。
手順は `.claude/orchestrators/banner-manual-orchestrator.md` と各スキルの `SKILL.md` にあるので、
ここでは「どの手順でも共通の判断基準」だけを書く。

セットアップ手順は [README.md](README.md) を参照。

## このシステムの目的

利用者自身の文章の1節を根拠に、Instagram の図解カルーセル（画像）とキャプションを作る。
生成 → 評価 → 保存 → 作成記録までを1回で完走させ、**保存したところで止まる。**

**Instagram へは投稿しない。通知も送らない。外へ何も出さない。**
投稿は、利用者が画像とキャプションを自分の目で確かめてから、自分の手で行う。

**どのアカウントで・誰に・何を発信するかは `config/brand.yaml` に書かれている。**
このファイルはジャンルに依存しない共通ルールだけを扱う。

## 発信ポリシー（厳守）

**作業開始時に必ず `config/brand.yaml` を読み込むこと。** 以下はそこから適用する:

| 参照先 | 何を決めるか |
|---|---|
| `account.purpose` | このアカウントが何のために発信するか |
| `audience.who` / `audience.pains` / `audience.vision` | 誰に向けて書くか。刺さる切り口の判断基準 |
| `tone.voice` / `tone.policy` / `tone.ng_words` | 書き方の憲法。**1つでも破ったら人に渡さない** |
| `offer.*` | 売りたいもの。CTAの文言と、誘導を入れる頻度 |
| `strategy_axes` | テーマの切り口の分類 |
| `hashtags.core` / `hashtags.wide` | キャプションのハッシュタグ |
| `design.palette` | 画像に使う固定3色 |

`brand.yaml` の `tone.policy` はこのシステムの安全弁であり、**オーケストレーターが勝手に
緩めてはならない**。読者の不安を材料にした投稿は、短期の数字が出ても中長期でアカウントの
信頼を壊すため、意図的に禁止している。

`brand.yaml` が未設定（雛形の `（...）` や `@your_account` が残っている・必須項目が空）のときは作らない。
これは指示文ではなく**スクリプトが止める**: 司令塔は最初に `check_brand.py` を実行する。
オーケストレーターがこの検査を迂回する手段を探してはならない
（検査に落ちたら、その旨を画面に出して止まる）。

## 画像は Pillow で描く（AI に文字を描かせない）

カルーセルの画像は、画像生成AIを使わない。`banner.py` が spec の文字を Pillow でそのまま描く
（ゴシック体固定・座標指定）。画像生成AIに日本語の文字組みをさせる方式は合格率が低く、
5枚すべてを上限内で通せないため（経緯は `.claude/skills/banner-production/references/carousel-spec.md`）。
evaluator の役割は「文言・発信ポリシー・構成」の判定。

## 実行の入口

利用者が「`banner-manual-orchestrator.md` に従って、カルーセルを1本作って」と頼むと、
Claude（メインセッション）が `.claude/orchestrators/banner-manual-orchestrator.md` を読み、
それに従って進める。初期設定（**最初に1回だけ**）は `.claude/skills/brand-setup/SKILL.md`。

**オーケストレーターは常にメインセッションであり、サブエージェントにしない。**
サブエージェントは自分の中からさらにサブエージェント（Task）を呼べないため、
オーケストレーターをサブエージェント化すると evaluator を起動できず、
評価ステップが実行不能になる（詳細は `.claude/orchestrators/README.md`）。

スクリプトは素の `python`（Mac は `python3`）で、**相対パス**で呼ぶ
（`.claude/settings.json` の許可リストが、この形の文字列との一致で判定されるため）。
時間のかかる処理は無いので、すべてフォアグラウンドで実行する。

## 生成→評価→改善ループ（厳守）

生成物（カルーセル画像 / キャプション）は、人に渡す前に必ず `evaluator` サブエージェントの
合否判定を通す。

```
生成 → evaluator が合否判定
  → 合格: 次ステップへ
  → 不合格: 修正指示付きで該当ステップだけ再実行（最大2回まで）
  → 2回で合格しない場合: 中止。生成物は output/ に退避し、どの段階で・なぜ中止したかを画面に出して止まる
```

再試行回数の上限は `config/loop-limits.yaml` で管理する。ここに書かれた上限を勝手に緩めない。

## 失敗時の安全側動作（厳守）

- どのステージで失敗しても「何も外へ出さない」に倒す。中途半端な生成物を、完成品のように見せない
- 失敗したら生成済み素材を `output/YYYY-MM-DD_<テーマ>/` に残す（原因を調べるため）
- 作成記録（`logs/created.jsonl`）への記録は、両方の評価が合格し、保存が終わった後にのみ行う
  （中止した回を記録すると、その節がしばらく選ばれなくなる）
- Instagram への投稿、外部サービスへの送信は、どんな理由でも行わない

## シークレット取り扱い（厳守）

- アカウントのパスワード・トークンなど、秘密の値を会話・生成物・ファイルに書かない。聞かない
- 利用者が秘密の値を貼ろうとしたら、止めて、貼らないよう伝える

## 投稿は「自分の文章の紹介」として作る（厳守）

投稿の中身は、利用者自身の文章（`config/brand.yaml` の `content_sources`。基本は `content/sources/*.md`）の
1節を根拠にする。1行のテーマだけから文言を起こすと、どの本にも書いてある一般論になり
中身が薄くなる。自分の文章には固有の数字・手順・理由・資料名が書かれているので、それを運ぶ。

- 司令塔が作成のたびに `build_article_index.py` を実行し、ネタ元を節（h2）ごとの
  根拠テキスト `content/articles/<スラッグ>/<節>-<内容ハッシュ>.md`（一度書いたら書き換えない。
  ネタ元が直されたら別名で作り直す）に切り出す。索引は `content/articles/index.json`、
  人が眺める一覧は `content/themes.md` のストック欄（どちらも自動生成。手で編集しない）
- `theme-picker` が返す **`source_path` を、構成・キャプション・evaluator の全員に渡す。**
  画面・キャプションに書く事実は、その節の本文にあるものだけ。自分の知識で補わない
- `source_path` 冒頭に「注意（この節を扱うときの縛り）」があれば、全員がそれに従う
  （`content_sources.cautions` に登録した語句が本文にある節に付く。例: 未確定の話は「検討中」と明記）
- evaluator は「ネタ元との照合」で、本文に無い事実・意味の改変・一般論だけの薄い枚を不合格にする
- 索引が無い・読めないときは投稿を作らない（根拠にできる文章が無い状態で作らない）

## テーマ重複防止

作る前に `content/articles/index.json`（紹介ネタの索引）と `logs/created.jsonl`（作成記録）を
必ず照合し、直近14日で使った節と、直近2件で紹介したネタ元を再利用しない。
`theme-picker` サブエージェントがこの照合を担う。`created.jsonl` に記録する `theme` は
theme-picker の出力を一字一句そのまま使う（突合はこの文字列の一致で行われる）。
記録は `record_created.py` が追記する。
