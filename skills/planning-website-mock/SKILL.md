# HP づくり：しっかり確認してからモック、素材がそろってから実装

HP を作る依頼が出たら、**参考サイトと22項目を本人と確認しきってからモック（完成イメージ）を作り、モックに必要な情報を受け取ってから実装する**。手戻りが一番高くつくのは「作ってから違うと分かる」ため。言葉で議論するより、先に見える形（モック）を作って確かめる。

## スキルの構成

```
planning-website-mock/
├── SKILL.md
└── references/
    ├── grill-items.md          … 22項目（正本）
    ├── tool-selection.md       … 公開先・保存先の選び方（目的 → 道具）
    ├── claude-design-guide.md  … Claude Design を初めて使う人への案内
    └── publish-guide.md        … Cloudflare Pages での公開を初めてする人への案内
```

## 起動したら最初にすること

最初の返信で「HP づくりの流れ（① 参考サイトを選ぶ → ② 22項目を確認する → ③ モック → ④ 情報を渡す → ⑤ 実装）で進めます。22項目の確認が終わるまでモックは作らず、情報がそろうまで実装しません」と一言宣言する。**宣言が出ていれば起動できている**と本人が分かる。宣言のあと、下の「進め方の確認」をする。

## 進め方の確認（起動したら最初に・キットの約束）

- **全体の流れを見せてから「1つずつ一緒に確認していきますか？（YES/NO）」と聞く。** YES なら1手順ずつ伝え、本人の「できた」などの合図を待ってから次へ。NO ならまとめて伝える
- 段の途中でも、手順が3つ以上ある作業（アカウント登録・キーの作成・公開など）に入るときは、その作業の流れを見せて同じように聞く
- **使う人の `~/.claude/CLAUDE.md` に同じルールが無ければ、初回に1度だけ「この進め方を CLAUDE.md にも入れますか？」と聞く。** 理由も添える（入れると、このキット以外の作業でも同じ進め方になる。入れなければ、このキットの中だけで効く）。OK のときだけ、出力のルールに次の1行を足す。黙って書かない
  > - 手順が3つ以上ある作業（設定・登録・導入など）は、**全体の流れを先に見せてから「1つずつ一緒に確認していきますか？（YES/NO）」と聞く。** YES なら1手順ずつ伝え、終わりの合図を待ってから次へ。NO ならまとめて伝える

## 流れ（5段）

各段の終わりの **▶ 確認** で本人の OK がなければ、次の段へ進まない。Claude が黙って判断を済ませると、本人が気づかないまま次へ進んでしまうため。

```
① 参考サイトを選ぶ
   本人: refero で URL を選んで貼る
   Claude: 値と「個性の要素」を 参考スタイル.md に保存
   ▶ 確認: 個性の要素の表を本人が OK

② 22項目を確認する（聞くタイミング・分け方は自由）
   Claude: 22項目を「聞く／決まっている／聞かない（理由）」の表で見せ、1問ずつ聞く
   ▶ 確認: 22項目すべての状態表を本人が OK → 要件.md に保存
          ＝ モックの入口

③ モックを作る（文章・写真は仮でよい）
   Claude: 下書きを作り、個性の要素と照らし合わせてから渡す
   本人: Claude Design で整える
   ▶ 確認: 本人が「モックで OK」

④ 情報を渡す
   Claude: モックから「素材リスト」を作り、受け取り用のフォルダとファイルも作って一覧で見せる
   本人: 画像はフォルダへ、文章は 素材テキスト.xlsx へ入れる（用意できないものは「仮で OK」と決める）
   Claude: 中身を読んで素材リストを更新
   ▶ 確認: 素材リストの全項目が「受け取り済み」か「仮で OK」
          ＝ 実装の入口

⑤ 実装する
   ⑤-1 実装計画（ページ一覧・作る順番・フォルダ構成・作り方）  ▶ 確認
   ⑤-2 トップを作る → 本人がブラウザで見る                    ▶ 確認
   ⑤-3 下層ページの構成を表で見せる → 作る → 本人が見る        ▶ 確認
   ⑤-4 動く仕組みを作る（外部サービスとの連携など）            ▶ 確認
   ⑤-5 公開（外に出す操作）                                   ▶ 確認
```

## 基本ルール

- **22項目の確認が全部終わるまでモックを作らない。** 聞くタイミングや分け方は自由だが、モックの前に全項目の状態（決まった／聞かない＋理由）を表で見せ、本人の OK をもらう
- **聞かない項目も、黙って飛ばさない。** 「聞かない」と判断したら、理由を表に書いて本人に見せる。本人が「聞いて」と言えば聞く
- **素材がそろうまで実装しない。** モックの OK のあと、すぐ実装に入らない。④で素材リストを見せ、全項目が「受け取り済み」か「仮で OK」になってから⑤に進む
- **実装も1段ずつ確認する。** ⑤の各段で本人の OK をもらってから次へ進む。トップの確認前に下層ページを作らない
- **参考サイトは本人が実物を見て選ぶ。** Claude は画面を見られないため、見た目の判断は本人に任せる。Claude が先に候補を絞ったり、言葉で方向を説明したりしない
- **参考サイトの個性は削らない。** 個性の要素は「全部残す」が初期値で、外すのは本人がそう言ったときだけ。Claude は「控えめにする」「1色に絞る」など、個性を減らす案を推奨しない。削るなら参考を選んだ意味がなくなり、平凡な仕上がりになるため
- **読みやすさとぶつかったら、消さずに置き方を変える。** 例: 線画が文字にかぶるなら位置をずらす。文字と背景の明暗差などの読みやすさの基準は守る
- **参考が2つ以上なら足し算で混ぜる。** 「土台はどちらで、もう一方から何を借りるか」を決める。土台の個性を消す借り方はしない
- **デザインの元データはファイルに残す。** 参考スタイル・要件・素材は案件フォルダの `design\` に保存し、モック・Claude Design・実装で同じものを使う。AI が見る情報を1か所にそろえておくと、食い違いが起きない。チャットだけに置くと、タブを移ったときに消える
- **難しい言葉は一言で説明する。** 初出のみ。言い換えを繰り返さない
- **道具の名前は役割が分かる形で書く。** 例: Cloudflare Pages ＝公開、D1 ＝保存。「Cloudflare」だけで済ませない（役割が複数あり混乱するため）

## ① 参考サイトを選ぶ

- **HP づくりでは必ず Refero Styles を最初に推奨する。** `https://styles.refero.design/` の URL を出し、参照するかどうかは聞かない。本人が「自分で探す」「Refero は使わない」と先に言っていても、一度は勧める（デザインの値が整理され、AI 向けの DESIGN.md がついているため、特徴を正確に写せる）。開けない・進めないと本人が言ったときだけ、本人が選んだ HP の URL で代替する
- **初めての人には使い方を1ステップずつ案内する。** Refero Styles は有名サービスの HP のデザイン（色・書体・余白）を2,000件以上集めたサイトで、各ページに DESIGN.md がある（ベータ版。無料の範囲・アカウントの要否は明記がないため、本人が開いて確かめる）
  1. URL を開く
  2. 上の検索欄に雰囲気の英語を入れる
  3. 「Trending / Popular / Newest」で並べ替え、カードを押してスタイルのページを開く
  4. 好みのページを2〜3個見つけ、1つに絞る
  5. そのページの URL をチャットに貼る
- 探し方のヒントを添える: 検索欄に雰囲気の英語を入れる（例: `white minimal`／`earthy`／`ocean`／`editorial`）。目的・ターゲットを先に聞いていれば、それに合う言葉を選ぶ
- 本人が気に入ったスタイルのページ URL（`/style/...`）を1〜3個、チャットに貼ってもらう
- Claude はそのページを読み、色・書体・余白・角丸と元 URL を `design\参考スタイル.md` に保存する。ページの DESIGN.md（AI 向けのデザイン指示書）があれば、その内容を優先して写す
- 値とは別に「**個性の要素**」の表を作る。このサイトがおしゃれに見える理由を、要素ごとに「なぜ効いているか」と並べて書く
- **▶ 確認:** 個性の要素の表を本人に見せ、OK をもらう

模範（Pa'lais の場合）:

| 個性の要素 | なぜ効いているか |
|---|---|
| 青い植物の線画が、区画をまたいではみ出す | 手描きのレシピ帳のような温かさ |
| 黄・オレンジ・ミントの有機的な色の形 | 料理の楽しさ・食欲 |
| 手書き書体の一言を見出しに添える | 人の声が聞こえる |

## ② 22項目を確認する

- 項目は [references/grill-items.md](references/grill-items.md)。下の「聞き方」で1問ずつ聞く
- **聞き方:** 1回に1問だけ。質問の UI（AskUserQuestion など）があれば使い、無ければチャットに同じ形で出す
  - 見出し: `確認 N問目 — 〈論点〉`
  - 本文: `決めたいこと: …` と `推奨: …（理由）`
  - 選択肢: A＝推奨、B〜D＝ほかの案（B→C→D の順に手間が増える）、E＝その他（自由に書く）
  - 分かることは聞かない（既存の資料・ファイルを先に読む）
- **聞くタイミング・分け方は自由。** おすすめは、目的・ターゲット・載せる内容の3問を①の前に聞くこと。誰に向けた HP かで合うデザインが変わり、参考サイトを選ぶヒントになるため
- 最初に22項目を「**聞く／決まっている／聞かない（理由）**」の表で見せる。分かることは聞かない（既存の資料、`参考スタイル.md` で値が決まったデザイン項目など）
- 目的・ターゲットの答えが①で選んだスタイルと合わないと分かったら、その場で伝え、①に戻るか本人に聞く
- 公開先・ドメインも22項目の中で決める。道具は目的から逆算して提案する（[references/tool-selection.md](references/tool-selection.md)）
- ターゲットや雰囲気の**具体例は案件ごとに聞く。** 他案件の値を持ち込まない
- **▶ 確認:** 22項目すべての状態表（決まったこと／聞かない＋理由）を本人に見せ、OK をもらう。OK のあと `design\要件.md` に保存する

表の模範:

| 区分 | 項目 | 状態 |
|---|---|---|
| 基本定義 | 目的・ゴール | ✅ 商品を知ってもらい、販売先へ案内する |
| 基本定義 | 競合と差別化 | ✅ ［決まった内容］ |
| 運用・技術 | 予算・納期 | ― 聞かない（テスト案件のため） |

## ③ モックを作る

- 入口条件: ②の ▶ 確認が終わっていること。終わっていなければ②に戻る
- **本人が先に「モックを作って」と頼んでも、未確認の項目が残っていれば作らない。** 22項目の状態表を出し、残りを聞いてから作る。急ぐ場合でも、未確認の項目を「聞かない（理由）」にするかを本人に決めてもらう
- 最初に「Claude Design を使ったことがありますか？」と聞く。**ない人には [references/claude-design-guide.md](references/claude-design-guide.md) の案内を1ステップずつ出す**。スキルを人に渡したとき、初めての人がここで止まらないようにするため
- Claude Design の既定デザインシステムが当たると、図解用の配色などが混ざってトンマナがずれる。**下書きの前に、案件用のデザインシステムを使うか、`参考スタイル.md` から新しく作るか、使わないかを確認する**
- Claude Code から Artifact の Design 型（デザイン用キャンバス）で**下書きを作る**。元にするのは `参考スタイル.md` と `要件.md`。このキャンバスは Claude Design と同じ編集画面で開ける
- 文章・会社情報は仮でよい。仮の文章は実在の情報と見分けがつくように、空欄は［住所］のように［ ］で書く
- **写真は枠だけにしない。** 仮の写真を入れる。写真が無いと、おしゃれかどうかを本人が判断できない
- **仮の写真は Openverse（`https://openverse.org/`）の CC0 から探す。** 検索の絞り込みでライセンスを CC0（権利を放棄した素材）にする。出所が分かり、モックを人に見せても権利の心配がないため。どの枠にどの写真を入れたか（元の URL）は `要件.md` に残す
- **仮の写真はモックまで。公開する HP には1枚も残さない**（⑤-5 で止める）。本人が「この写真で十分」と思い込まないよう、モックを渡すときに「写真は仮です。公開前に全部替えます」と伝える
- **渡す前に、個性の要素の表と下書きを1項目ずつ照らし合わせる。** 抜けていたら入れてから渡す。照らし合わせた結果も本人に伝える
- 本人が Claude Design で整える。Claude は画面を見られないため、見た目の確認は本人にお願いし、1回の返信で1ステップだけ案内する
- **▶ 確認:** 本人が「モックで OK」と言ったら、モックの URL を `要件.md` に残す

## ④ 情報を渡す

- 入口条件: ③の ▶ 確認が終わっていること
- **モックから素材リストを作り、一覧で見せる。** モックを上の区画から順に見て、仮の文章・［ ］の空欄・仮の写真・仮のロゴ・外部のアカウントや URL を1つずつ拾う。モックにない下層ページ（`要件.md` のページ構成）で要る情報も、「モック外」として同じ表に入れる
- 1行に1つの素材。「どこに使う何か」「どんな形で渡してほしいか」が分かるように書く。写真は向き（横長・正方形など）・枚数・目安の大きさを添え、**本人が使う権利を持っているもの**に限ると伝える
- 素材リストは `design\素材\素材リスト.md` に保存する
- **④に入ったら、素材リストと一緒に受け取り用のフォルダとファイルを作る。** 本人が置き場所を考えなくて済むようにするため
  - 画像: 1素材に1フォルダ。`design\素材\画像\<番号>_<何の写真か>_<向きと枚数>\`（例: `21_商品の写真_正方形3枚`）。フォルダ名だけで何を入れるか分かるようにする
  - 文章: `design\素材\素材テキスト.xlsx` に1素材1行で「番号・素材・使う場所・いまの中身（仮）・渡す中身・状態」を並べる。本人が書く「渡す中身」の列だけ黄色にし、上に書き方の説明1行と例の行を置く。Markdown に慣れていない人が多く、Excel なら迷わないため
  - 作るのは「⬜ 未」の項目だけ。本人が「仮で OK」にしたものは作らない
  - 本人が「入れた」と言ったら、フォルダとファイルを読んで素材リストの状態を更新する。空のフォルダ・空欄は「⬜ 未」のまま
- 受け取りは区分ごと（会社情報 → 商品 → 写真 → …）に進め、1回で全部を求めない
- 用意できない素材は、本人が「仮で OK」と決める。Claude が勝手に仮のまま進めない
- **写真の「仮で OK」は実装までの約束。** 写真を「仮で OK」にするときは、「実装は進められますが、公開の前に本人の写真へ替えるか、その写真の枠を外すかを決めてもらいます」と先に伝える
- **▶ 確認:** 素材リストの全項目が「受け取り済み」か「仮で OK」になったら、本人に一覧で見せて OK をもらう

素材リストの模範:

| # | 区分 | 使う場所 | 素材 | 渡してほしい形 | 状態 |
|---|---|---|---|---|---|
| 1 | 文章 | トップ／フッター | 会社の住所 | テキスト | ⬜ 未 |
| 2 | 画像 | トップ／ヒーロー | 商品の写真（3種） | 正方形に切り抜ける写真 各1枚・長辺1600px 以上 | ⬜ 未 |
| 3 | 画像 | トップ／写真の帯 | つくっている風景の写真 | 横長 1枚・長辺2000px 以上 | ✅ 受け取り済み |
| 4 | アカウント | トップ／note の新着 | note のアカウント名 | テキスト | 🟨 仮で OK |

## ⑤ 実装する

- 入口条件: ④の ▶ 確認が終わっていること
- **⑤-1 実装計画:** ページ一覧・作る順番・フォルダ構成・作り方（②で決めた道具）を見せて OK をもらう。計画には下の「写真の差し替え表」を含める
- **写真は「同じ名前で上書き」で差し替えられる作りにする。** スキルを渡した人が、HP を作ったあとに自分で写真を直せるようにするため
  - 写真は公開フォルダの `img\` にまとめ、**使う場所が分かる名前**にする（例: `product-moshio.jpg`、`top-band.jpg`）。拡張子は写真なら `.jpg`、ロゴなら `.png` にそろえる
  - 見た目は写真の縦横比に左右されないように作る（`object-fit: cover` で枠に合わせて切り抜く）。どんな写真で上書きしても崩れないようにするため
  - 公開フォルダの外（案件フォルダの直下）に `写真の差し替え表.xlsx` を作る。列は「ファイル名・使うページと場所・向き・おすすめの大きさ・いまの写真・仮かどうか」。仮の写真は「仮かどうか」の列に「仮（Openverse）」と書き、セルを赤くする。名前は替えないので、仮かどうかはこの列で見分ける。上に差し替え方（同じ名前・同じ拡張子で上書き → 公開の操作）を1行書く。公開フォルダに入れると表まで公開されるため外に置く
  - 受け取った大きな写真は、長辺1600px 前後の JPEG に縮めて `img\` に置く。元のファイルは `design\素材\画像\` に残す
- **⑤-2 トップ:** モックどおりに作る。Claude は画面を見られないが、ブラウザを画面なしで動かして撮影できる環境なら、撮影で崩れを確かめてから渡す。そのうえで本人にブラウザで見てもらい OK をもらう
- **⑤-3 下層ページ:** モックがないページは、作る前に「区画の並び」と「載せる中身」をページごとの表で見せて OK をもらう。作ったあと本人に見てもらう
- **⑤-4 動く仕組み:** 外部サービスとの連携など、動作を本人と確かめる
- **⑤-5 公開:** 外に出す操作なので、必ず本人の OK をもらってから行う。テスト案件なら、検索エンジンに載らない設定（noindex）を入れるか聞く。進め方は [references/publish-guide.md](references/publish-guide.md)。**公開は Claude がコマンドで自動で行うが、実行する作業は1つずつ「何をするか・何が起きるか」を見せて OK をもらってから実行する**（人がやるのはアカウント作成・メールの確認・「Authorize」の3つだけ）
- **公開の前に、仮の写真が0枚かを確かめる。** テスト公開も含む。`写真の差し替え表.xlsx` の「仮かどうか」と素材リストを見て、仮の写真が1枚でも残っていたら公開しない。その写真ごとに「本人の写真に替える」か「その写真の枠を外す」かを本人に選んでもらい、0枚になってから公開の操作に入る。本人が「仮のままで公開して」と言っても公開しない。権利の確認をしていない写真や、実物と違う写真を外に出すことになるため

## 完了条件

- ③: 本人が「モックで OK」と言った
- ④: 素材リストの全項目が「受け取り済み」か「仮で OK」になり、本人が OK した
- ⑤: 各段で本人の OK をもらい、仮の写真が0枚の状態で公開した
- `design\参考スタイル.md`（値・個性の要素）、`design\要件.md`（22項目の状態・道具の構成・モックの URL）、`design\素材\`（素材リスト・素材テキスト・画像フォルダ）、`写真の差し替え表.xlsx` が残っている
