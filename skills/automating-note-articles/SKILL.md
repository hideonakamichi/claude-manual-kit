# note 記事キット（入れて、動かす）

キットの中身（3人の手順書・スクリプト・README）は `template\` が正本。案件にはコピーして使う。
**仕組みの説明・つなぎ方の表・使い方は `template\README.md` が正本**（ここに同じことを書かない）。

```
① 置き場所を決める → ② サーバーを確認 → ③ ひな形をコピー → ④ 通知先を決める（試し送りまで）
→ ⑤ 設定を埋める → ⑥ キーを用意（必要なときに案内）→ ⑦ DB を作る → ⑧ 手動で1周 → ⑨ 定期実行（聞いてから）
```

各段の確認が済むまで次へ進まない。

## 進め方の確認（起動したら最初に・キットの約束）

- **全体の流れを見せてから「1つずつ一緒に確認していきますか？（YES/NO）」と聞く。** YES なら1手順ずつ伝え、本人の「できた」などの合図を待ってから次へ。NO ならまとめて伝える
- 段の途中でも、手順が3つ以上ある作業（アカウント登録・キーの作成・公開など）に入るときは、その作業の流れを見せて同じように聞く
- **使う人の `~/.claude/CLAUDE.md` に同じルールが無ければ、初回に1度だけ「この進め方を CLAUDE.md にも入れますか？」と聞く。** 理由も添える（入れると、このキット以外の作業でも同じ進め方になる。入れなければ、このキットの中だけで効く）。OK のときだけ、出力のルールに次の1行を足す。黙って書かない
  > - 手順が3つ以上ある作業（設定・登録・導入など）は、**全体の流れを先に見せてから「1つずつ一緒に確認していきますか？（YES/NO）」と聞く。** YES なら1手順ずつ伝え、終わりの合図を待ってから次へ。NO ならまとめて伝える

## ① 置き場所を決める

- HP 制作キットがある案件 → その案件フォルダに `note-agent\` として置く（`design\` `site\` と並べる）
- HP が無い案件 → 案件フォルダに `note-agent\` だけ
- 既に `note-agent\` があれば上書きしない。中身を見て、キットの更新か新しく入れるかを本人に聞く

## ② サーバーを確認する（必ず・推奨つき）

記事の保存先を **Supabase か Cloudflare（D1）か** 本人に選んでもらう。判断は、HP 制作キット（別配布）に同じ表がある。無ければ次の順で決める: ①HP がどこにあるか（Cloudflare なら D1）→ ②使う間隔（7日より空くなら、無料枠が一時停止する Supabase は避ける）→ ③画像をネットに置く必要があるか（無ければ PC）。表（または3つの順）を見せ、推奨と理由を添える。

- **推奨: Cloudflare D1 ＋ 画像は PC。** キットはこの形で作ってある
- Supabase を選んだとき: `scripts\db.py`（と画像をネットに置くなら `gen_image.py`）を Supabase 向けに書き直す必要がある。手間を伝えてから進む
- 人から受け取った仕組み（例: Supabase 前提のキット）でも、そのまま使わずにここで選び直す

## ③ ひな形をコピーする

`template\` の中身を `note-agent\` に丸ごとコピーする（`.env.local` は作らない）。コピーのあと README の「この案件で決めたこと」に②の結果と理由を書く。

## ④ 通知先を決める（必ず・試し送りまで）

自動実行の結果を知る手段は通知だけ。届かないまま動くと、費用だけかかって誰も気づけない。だから設定より先に済ませる。

1. **「毎日開くものはどれですか」と聞く**（Gmail・Slack・Discord・Chatwork・LINE。複数可）
2. その中で、README「通知先の選び方」の表のハードルが一番低いものを、理由つきですすめる（Discord → Slack → Gmail → Chatwork → LINE の順に低い）。Chatwork は有料プラン、LINE は公式アカウントづくりが要ることを必ず伝える。料金・条件は変わるので、案内する前に公式ページで確かめ、確かめた日を添える
3. 決まったら `.env.local.sample` を `.env.local` にコピーし、`NOTIFY_CHANNEL` とその欄を **本人が** 埋める（手順が3つ以上なので、流れを見せて「1つずつ確認しますか？（YES/NO）」と聞く。値はチャットで受け取らない）
4. `python scripts\notify.py check` → `python scripts\notify.py test` を動かし、**本人が「届いた」と言うまで次へ進まない**
5. 選んだ通知先と理由を README の「この案件で決めたこと」に書く

- Gmail のアプリ パスワードは https://myaccount.google.com/apppasswords （2段階認証がオンでないと出ない）
- 自動実行（run-agent.ps1）は、通知の設定が無いと記事を書かずに止まる。送れなかった通知は `work\未送信\` に残り、次の起動で送り直す。自動実行が途中で止まったときは「失敗」が1通届く
- 前のキット（notify_mail.py・Gmail だけ）で作った案件は、`NOTIFY_CHANNEL` が空でも Gmail の欄が埋まっていれば Gmail として動く

## 記事に必要な情報の集め先（⑤の前に、依頼主へ頼む）

キットは、**もらった情報だけで記事を書く**。もらえていない情報は推測で埋めず、空欄のまま止まる。だから先に、何を・誰に・どこからもらうかを決めて、依頼主（会社の担当者）に頼む。

| 必要な情報 | もらう先（誰・どこ） | 書く場所 |
|---|---|---|
| 読者・記事の目的・トーン | 依頼主へのヒアリング。HP 制作キットがあれば要件書から写す | `media.config.json` の reader・goal・tone |
| 会社・商品の事実（社名・所在地・創業・商品の特徴・価格など） | 会社の公式サイト・パンフレット・商品ページ。分からない点は担当者に聞く。**本人が確かめたものだけ**、出所つきで | `facts\確かめた事実.md` |
| 商品名と販売ページの URL | 販売ページ（自社サイト・通販サイトなど）を担当者に教えてもらう | `media.config.json` の products |
| 現場の言葉・様子（インタビュー風・密着のときだけ） | 取材。担当者への聞き取り、現場の見学・写真・動画。名前を出してよいかも確かめる | `facts\取材メモ.md` |
| 言えないこと（業界の決まり・広告の規制） | 依頼主の社内ルール、業界団体や官公庁のガイドライン。依頼主に「広告で言えないことはありますか」と聞く | `media.config.json` の forbidden |
| 信頼できる出典 | 官公庁・大学・業界団体・メーカー公式。**ドメインは実際に開いて確かめる** | `media.config.json` の trusted_sources |
| 画像の見た目 | 依頼主のロゴ・配色・ブランドの資料、HP の配色。無ければ本人に聞く | `media.config.json` の image_style |
| note のアカウント名 | 依頼主（note.com/ のあとの文字列） | `media.config.json` の note_user |
| 記事のネタ（読者の疑問） | 問い合わせ・よくある質問・営業現場の声、検索キーワード。編集長が案を出し、本人が選ぶ | ネタ帳（編集長の手順書） |

- 上の表のうち、**依頼主から聞かないと分からないもの**（目的・事実・言えないこと・取材）は、⑤に入る前に一覧にして渡し、返事を待つ
- 返事が来ていない欄は空欄のままにして、先へ進まない（会社の発信として外に出るため）

## ⑤ 設定を埋める（1問ずつ）

`media.config.json` の（）を全部埋め、`facts\確かめた事実.md` を作る。

- **HP 制作キットがあるときは、先にそこから写す**（README「HP キットとのつなぎ方」の表）。読者・目的 ← `design\要件.md`、事実 ← 素材リストの ✅ だけ、色 ← `参考スタイル.md`、note_user ← `NOTE_USER`
- 写せないものだけ、1問ずつ聞く。推奨を添える。聞く順: **記事のテイスト（下）→ 画像のテイスト（下）** → 字数 → 話者の名前と役（話者ありのとき）か書き手（地の文のとき）→ 商品と URL → 言えないこと（業界の決まり）→ 信頼できる出典
- 信頼できる出典（trusted_sources）に業界団体を書くときは、**ドメインを実際に開いて確かめる**（名前から推測したドメインが別の団体のものだった、ということが実際にあった）
- **確かめた事実は本人が確かめたものだけ。** 仮の素材・推測は入れない（会社の発信として外に出るため）
### 記事のテイストを決める（必ず本人に聞く・見本つき）

**テイストは記事ごと。** 編集長がネタ1本ずつにテイストと理由をすすめ、本人が採用のときに確かめる（変えるときは `topics.py style 番号 テイスト`）。ここで決めるのは次の2つ。

- `styles`: この案件で使ってよいテイスト（複数）。編集長はこの中からだけすすめる
- `article_style`: 既定（テイストが空の記事・迷ったとき）。推奨は dialogue

**言葉だけで選ばせない。** 案件のテーマ1つ（例: 「〇〇を A で食べるとどう変わるか」）を、各テイストで2〜3行ずつ書いた見本を先に見せる。

| テイスト | 向いている場合 | 条件 |
|---|---|---|
| dialogue 2人の対話（**推奨・既定**） | 疑問の順に話が進み、最後まで読まれやすい。どの業種でも使える | 質問役と解説役の名前 |
| interview インタビュー風 | 職人・社長など人柄や思いを出したい | **本人の取材メモが要る** |
| essay 読み物 | 落ち着いた印象にしたい | 書き手（narrator） |
| story ストーリー＋解説 | 使う場面を思い浮かべてほしい | 場面は例え話だと分かる書き方 |
| howto ノウハウ・まとめ | 検索で「やり方」を探す読者が多い | 手順の箱が必須 |
| documentary ドキュメンタリー・密着 | 作る現場・一日の流れを見せたい | **本人の取材メモが要る** |

- interview・documentary を選んだら、**会社の人の言葉・現場の様子を AI が作ってしまう危険**を伝える。本人が実際に聞いた言葉・見た様子を `facts\取材メモ.md` に書くのが条件。無いまま書こうとすると機械チェック（E17）で止まる
- story を選んだら、場面は「たとえば〜」の例え話にとどめ、お客さんの声や実際の出来事のようには書かないと伝える
- 「！」の回数は、話者ありは `exclamations`、地の文は `exclamations_prose`（既定 0〜5。対話より少ないのが自然）
- 任せきりにしない理由: 編集長が取材メモの要るテイストを勝手に選んだり、同じテイストに偏ったりしないよう、最後は本人が決める
- 前のキットで作った DB は、`python scripts\db.py init` をもう一度動かすとテイストの欄が足される（中身は消えない）。テイストが空の古い記事は `article_style` で書く

### 画像のテイストを決める（必ず本人に聞く・見本を1枚作ってから決める）

`image_style`（見た目）・`image_avoid`（避けること）・`image_reference`（見本）を決める。

- **HP があるとき**: 公開済みなら URL、まだなら `design\参考スタイル.md` とモックを見て、色・タッチ（線画・水彩・写真風など）・余白を写した案を出す。HP と記事の画像がそろうように、`image_reference` に HP の URL（公開前ならスクリーンショットのパス）を入れる
- **HP が無いとき**: タッチの選択肢（フラットな線画／水彩／写真風／手描き風）を見せ、推奨を添えて選んでもらう
- **避けることも必ず書く**（例: 線画なら「水彩・写真風・グラデーション」）。ある案件では「フラット・線画」と頼んだのに水彩っぽい画像ができた
- 決めたら見本を1枚作る（manual なら指示文を出し、本人が ChatGPT などで作る）。本人の OK が出てから確定する。そろわなければ `image_style` と `image_avoid` を直してもう1枚

- 埋めたら `python scripts\db.py` を引数なしで1回動かす。使い方が出れば設定が読めている（JSON の書き間違いならエラーが出る）

## ⑥ キーを用意する（必要になったときに案内）

使うものと使い道・費用を表で見せ、**入れるかどうかは本人が決める**。キーの値はチャットで受け取らない（本人が `.env.local` に直接書く）。

| キー | 使い道 | 無いとき |
|---|---|---|
| Cloudflare のアカウント ID と API トークン（権限は D1 の編集だけ） | 記事の保存 | 動かない |
| Gemini | 見出し画像・図解（`image_mode: gemini` のときだけ） | 下の「画像の作り方を決める」 |
| Jina（**推奨**・無料のキー） | Web 検索（出典集め） | ページを読むだけなら動く。ただし出典が集まらず差し戻されやすい |

- Cloudflare はメールアドレスの確認が済んでいないと、トークンの作成が「An unknown error occurred / Please verify your email.」で止まる。先に確認メール（無ければダッシュボードの Resend）を案内する。確認のあとも同じエラーなら、ログアウトしてログインし直すと通る（開いたままの画面には古い状態が残るため）。トークンの画面の「Test this token」のコマンドはコピー不要（動作は db.py で確かめる）

### 画像の作り方を決める（必ず本人に聞く・料金つき）

Gemini の画像モデルは **無料枠では使えない**（条件は変わるので、案内する前に公式で確かめる。確かめた時点では、無料のキーだと 429・limit: 0 になり、別の Google アカウントでも同じだった）。次の表を見せて選んでもらう。

| | manual（無料・既定） | gemini（有料） |
|---|---|---|
| 画像を作るのは | 人。ライターが指示文と画像の名前を出し、人が ChatGPT・Canva などで作って `note下書き\{番号}\images\` に入れる | Gemini が自動で作る |
| 人の手間 | 1記事に画像2枚ほど作って入れる | なし |
| 費用の目安 | 0円 | 1枚 約0.039ドル（2.5-flash-image）〜約0.067ドル（3.1-flash-image・1024px）。1記事2枚で約12〜20円（1ドル150円で計算） |
| 準備 | なし | 支払い情報の登録。最初に 5ドル以上の前払いを求められることがある |

- 料金は変わる。案内する前に https://ai.google.dev/gemini-api/docs/pricing で確かめ、確かめた日を添える
- どちらでも、下書き.html を**ブラウザで**開き（VSCode ではコードが出るだけ）、ボタンを①から順に押して note で Ctrl+V するだけで、文章と図解が記事の形で入る（図解のあとは Enter を1回）。見出し画像だけは note の画像ボタンから1枚選ぶ（note の見出し画像は約1.91:1 なので、16:9 は上下が少し切れる。切り取りの枠で文字が欠けないよう合わせる）
- **note の貼り付けの決まり**（試して確認した）: 文章だけ→見出し・太字・リンク・引用が残る／画像だけ（画像としてコピー）→入る／文章と画像をまとめて→全部消える／ネット上の画像の URL→消える。画像を貼るとカーソルがキャプションに移るので Enter で本文に戻る。タイトルの欄に貼ると書式が全部消える（本文の欄をクリックしてから貼る）
- note へ貼るのは人の手で行う。ブラウザ自動操作で下書き保存まで自動にする案は検討して見送った（公式 API が無く、手段はブラウザ操作か非公式の裏口だけ。週1本なら手貼りは数分で、作る手間と note の画面変更で壊れる保守のほうが重い）。本数が増えて本人が望んだら考え直す
- 選んだ方を `media.config.json` の `image_mode` に書き、README の「この案件で決めたこと」に理由と一緒に残す

**gemini（有料）を選んだら、続けて支払いの登録を案内する**（手順が3つ以上なので、流れを見せて「1つずつ確認しますか？（YES/NO）」と聞く）:

1. https://aistudio.google.com/apikey でキーを作る（まだなら）→ `.env.local` の `GEMINI_API_KEY=` に本人が貼る
2. AI Studio の API キーの画面（または Projects の画面）で、キーのプロジェクトの「Billing Tier」の欄にある **Set up billing** を押す
3. 国を選び、規約に同意し、連絡先と支払い方法（カード）を入れる（Google の請求先が既にあれば選ぶだけ）
4. 「Prepay（前払い）」か「Postpay（後払い）」を選ぶ画面が出たら選ぶ。前払いを求められたら最低 5ドル
5. 終わったら Claude が `python scripts\gen_image.py test check "簡単な絵の指示"` を1回動かし、`images\test-check.png` ができることを確かめる（1枚分の費用がかかると先に伝える）。できた試しの画像は消す
6. 安いモデルにしたいときは `.env.local` の `GEMINI_IMAGE_MODEL=` を `gemini-2.5-flash-image` にする

## ⑦ DB を作る

`python scripts\db.py init`。実行前に「Cloudflare に DB（名前は d1_database）ができる」ことを伝えてから。

## ⑧ 手動で1周する

`note-agent\` を作業フォルダにして「編集長を起動して1周回して」。初回はネタ候補が出て止まるので、本人に選んでもらい（`topics.py adopt`）、もう1周で記事まで通す。

- **記事の周に入る前に Jina のキーを確かめる**（`python scripts\web.py key`）。無ければ、入れるかを推奨つきで聞く（編集長の手順 media-pipeline の「Jina のすすめ方」）。⑥で入れなかった人にも、ここでもう一度だけ聞く

- 止まった所・差し戻しの理由を本人と見る。直す所が手順書やスクリプトなら **正本（`template\`）を直してから案件へコピーする**
- 合格したら `note下書き\` の `下書き.html` を本人と開き、note に貼れるか確かめる

## ⑨ 定期実行（本人に聞いてから）

手動で1周うまく回ってから提案する。Windows のタスク スケジューラに `scripts\run-agent.ps1` を週1で登録する。登録は PC に残る設定なので、**何が・いつ動くかを説明して OK をもらってから**行う。

## キットを直すとき

- 3人の手順書・スクリプト・README は `template\` が正本。直したら、使っている案件の `note-agent\` へコピーする（`media.config.json` `facts\` `.env.local` は上書きしない）
- `media.config.json` の `_kit` に直した日付を入れ、どの案件が古いかを分かるようにする
- 「必ず〜する」を足すときは、ライターの手順書・レビュアーのチェックリスト・`check_article.py` の3か所に同じ番号で入れる
- 案件だけの値は手順書に書かず `media.config.json` に足す

## 完了条件

- `note-agent\` に `media.config.json`（（）が残っていない）と `facts\確かめた事実.md` がある
- README の「この案件で決めたこと」にサーバーの選択と理由、通知先と理由がある
- `notify.py test` の試しの通知が本人に届いた
- 手動で1周し、合格記事の `下書き.html` を本人が見た（または、どこで止まっているかを本人が知っている）
