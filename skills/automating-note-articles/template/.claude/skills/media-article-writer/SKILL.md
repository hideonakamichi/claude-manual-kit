# note 記事の書き方（ライター専用）

> **先に `media.config.json` を Read する。** この手順の `{質問役}` `{解説役}` `{会社}` `{読者}` などは、その値に置き換えて読む。
> 対応: {会社}=company / {読者}=reader / {目的}=goal / {トーン}=tone / {テイスト}=**記事の style**（`db.py get` で出る。空なら article_style）/ {質問役}=characters.asker / {解説役}=characters.explainer / {書き手}=narrator / {取材メモ}=interview_file / {字数}=length / {見出し数}=h2 / {！の回数}=exclamations（地の文のテイストは exclamations_prose）/ {商品}=products / {信頼できる出典}=trusted_sources / {言えないこと}=forbidden / {画像の見た目}=image_style / {避けること}=image_avoid / {見本}=image_reference

## 目的

{読者}に向けて、{目的}。
{トーン}。商品は話の流れで自然に出し、{商品} の url へ案内する。

## 流れ

```
1. 記事を読む（ネタ・切り口・触れる商品・テイスト（style）。差し戻しならレビュアーの指摘も）
   python scripts/db.py get {id}
2. 会社・商品の事実を読む → facts/確かめた事実.md（ここに無いことは書かない）
   {テイスト}が interview / documentary なら {取材メモ} も読む。無い・中身が無いなら書かずに止まり、
   「取材メモが無いので書けない」と編集長に返す（発言・場面を作らないため）
3. 調べる（出典はその場で research_notes に記録。あとから思い出さない）
4. 書く（下の書き方に厳密に従う）→ work/article_{id}.md
5. 画像を作る（見出し画像1枚 + 図解1枚以上。省かない）
6. 事実確認（4段階）
7. 提出前の検証（3段階）→ DB に保存
8. 編集長に報告
```

## 3. 調べる

```bash
python scripts/web.py search "調べたいこと" --out work/search_{id}_1.txt   # 検索（キーが無ければ使えない → read だけで進める）
python scripts/web.py read https://... --out work/src_{id}_1.txt               # 本文を保存して Read で読む
```

- 信頼できる出典を優先: {信頼できる出典}
- 個人ブログ・まとめサイトだけを根拠にしない
- 検索の上位はマスコミ・SNS・Q&A サイトになりやすい。信頼できる出典が出てこないときは `site:` でしぼって検索し直す（例: `"〇〇 食べ方 site:ac.jp"`、`"〇〇 基準 site:go.jp"`。業界団体は名前かドメインを入れる）
- 会社・商品のことは facts/確かめた事実.md だけ。{商品} の url のページは読めたら引用してよい（読めなければ書かない）

### research_notes（必須）

`work/notes_{id}.json`:

```json
{
  "collected_at": "YYYY-MM-DDTHH:MM:SS+09:00",
  "writer_agent": "media-writer",
  "sources": [
    {
      "url": "https://example.go.jp/...",
      "title": "ページの題名",
      "accessed_at": "YYYY-MM-DDTHH:MM:SS+09:00",
      "extracted_via": "jina-reader",
      "quotes": [
        { "text": "ページにある文をそのまま", "used_in": "## 見出し名 の {解説役}の2つ目の発言" }
      ]
    },
    {
      "url": "facts/確かめた事実.md",
      "title": "確かめた事実（会社・商品）",
      "extracted_via": "local",
      "quotes": [ { "text": "所在地は〇〇県〇〇市", "used_in": "..." } ]
    }
  ]
}
```

- `sources` は **3件以上**、うち **信頼できる出典（上の種類）が1件以上**
- 記事に書いた数字・固有名詞・「〜と言われている」は、必ず対応する `quotes` を残す。引用できないものは書かない
- `reviewer_verifications` は書かない（レビュアーが足す）

## 4. 書き方

### テイスト（{テイスト}）ごとの形（最初に確かめる）

| {テイスト} | 文章の形 | 始まり方 | 中身の順番（目安） |
|---|---|---|---|
| dialogue（2人の対話） | 話者あり。全部が発言 | `**{質問役}**: ` の質問 | 下の「中身の順番」 |
| interview（インタビュー風） | 話者あり。最初の `##` の前にリード文（地の文）を3段落まで | リード文で、誰に何を聞くかを示す → `**{質問役}**: ` の質問 | 話す人の紹介 → 仕事・こだわり → 読者に役立つ話 → 商品 → 締め |
| essay（読み物） | 地の文。{書き手}が語りかける | 読者への問いか、身近な場面 | 疑問 → 理由（出典つき）→ やってみる → 失敗しやすい所 → 商品 → 締め |
| story（ストーリー＋解説） | 地の文。前半は場面、後半は解説 | 「たとえば、こんな夕食の場面」のような例え話の場面 | 場面 → なぜそうなるか（出典つき）→ やってみる → 商品 → 場面に戻って締め |
| howto（ノウハウ・まとめ） | 地の文。手順と要点が中心 | 読者の困りごとを1文で | 結論 → 手順（:::steps 必須）→ コツ（:::point）→ 失敗（:::caution）→ 商品 |
| documentary（ドキュメンタリー・密着） | 地の文。見たこと・聞いたことを時間の順に | {取材メモ}にある場面 | 場面を時間の順に → 読者に役立つ話（出典つき）→ 商品 → 締め |

- **interview と documentary の発言・場面は {取材メモ} にあるものだけ。** 言葉を足さない・言い換えで意味を変えない。メモに無い人物・出来事を作らない
- **story の場面は例え話だと分かる書き方にする。** 実在のお客さんの声・実際にあった出来事のように書かない（「お客さんから〜と言われました」は書かない）

### 話者ありのテイスト（dialogue・interview）の役割（絶対に守る）

- **{質問役}**＝質問役（characters.asker.role）。「〜ですか？」と聞く側。interview では聞き手
- **{解説役}**＝解説役（characters.explainer.role）。具体的に答える。**会社・商品について話せるのは確かめた事実だけ**（interview では {取材メモ} の言葉も）
- 逆転禁止（{解説役}が聞いて{質問役}が答えるのは NG）。dialogue は**必ず `**{質問役}**: ` の質問から始める**。interview はリード文のあと、最初の発言を `**{質問役}**: ` の質問にする

### 地の文のテイスト（essay・story・howto・documentary）

- 書き手は {書き手}。読者に「〜ですよね」と語りかける調子で、{トーン}
- **`**名前**:` の形は使わない**（話者の書き方のため）。人の言葉を入れるときは「」で地の文の中に書く（documentary は {取材メモ} の言葉だけ）
- 1段落は4文まで（スマホで読みやすい長さ）。段落と段落の間は1行あける
- 「この記事では〜」「今回は〜」で始めない

### 使える書き方（note で表示できるものだけ）

| 書き方 | 使う場所 | note での見え方 |
|---|---|---|
| `**{質問役}**: 本文` / `**{解説役}**: 本文` | 話者ありのテイストだけ。1発言＝1行 | 名前が太字の段落 |
| 地の文の段落 | 地の文のテイスト（interview はリード文だけ）。1段落＝1行 | 普通の段落 |
| `## 見出し` | {見出し数}個 | 大見出し |
| `### 小見出し` | 必要なときだけ | 小見出し |
| `![説明](images/{id}-fig1.png)` | `## 見出し` のすぐ次 | 画像（人が入れ直す） |
| `:::point{title="..."}` 〜 `:::` | 覚えてほしいこと。1つ以上 | 引用の箱 |
| `:::caution{title="..."}` 〜 `:::` | 失敗しやすいこと | 引用の箱 |
| `:::steps` 〜 `:::` | 手順。中は `1. ` の番号リスト | 番号リスト |
| `**強調**`（後ろにコロンを付けない） | 発言の中 | 太字 |
| `[商品名](https://www.amazon.co.jp/dp/ASIN)` | 商品に触れるとき1回 | リンク |

- **使わない**: 表（`|`）・水平線（`---`）・`<mark>`・H1（`# `）・導入文（「この記事では〜」）
- dialogue は箱の外・発言の外に地の文を置かない。どのテイストでも、リストは箱の中だけ
- `**名前**:` の形は話者専用（地の文のテイストでは使わない）。話者のあとのコロンは半角 `:` と半角スペース
- 1行目に見出し画像を書く: `<!-- EYECATCH images/{id}-eyecatch.png -->`

### 長さとテンポ

- 本文 **{字数}字**（記号・URL を除いて数える）
- 話者あり: 1発言は6文まで。4〜7往復に1回、10〜25字の短い相づち（「えっ、そうなんですか！」「なるほど」）
- 地の文: 1段落は4文まで。3〜4段落に1回、短い1文の段落で間をつくる
- 「！」は {！の回数}回、「(笑」は2回まで
- 数字はやわらかく（「ひとつまみ、だいたい1gくらい」）。ただし数字には出典が要る

### 中身の順番（dialogue の目安。ほかのテイストは上の表）

1. {質問役}の疑問から入る（例: 「〇〇って、AとB、どっちにしてます？」）
2. なぜそうなるのか（一般的な理由。出典つき）
3. 実際にやってみる（:::steps で手順）
4. 失敗しやすいところ（:::caution）
5. 商品の提案（facts の「提案としてなら書けること」の範囲。商品リンク1回）
6. 締め（{質問役}の「やってみます！」と{解説役}の一言）

### 見出しのつなぎ

各 `##` の最初の発言（地の文なら最初の段落）で「ここで何を話すか」を1文で示し、最後の発言（段落）で次の見出しへつなぐ。
例: 「**{質問役}**: 理由はわかりました！じゃあ家で試すなら、どうすればいいんですか？」→ `## 家でやってみる`
例（地の文）: 「理由がわかったところで、家で試す方法を見ていきましょう。」→ `## 家でやってみる`

### 言ってはいけないこと

- {言えないこと}（forbidden.words とその言い換え。理由は forbidden.reason）
- 会社・商品の、確かめた事実に無いこと（製法・歴史・こだわり・価格・内容量・受賞）
- 相対の時制（今年・最近・もうすぐ）。「2026年10月」のように絶対の日付で書く
- AI 臭い言い回し: することができます／幅広く／包括的に／網羅的に／一助となれば／について解説します／いかがでしたでしょうか／まとめると以下／整理すると／第一に／したがって／でございます／いたします／ご紹介します

### お手本（形だけ。〇〇・A・B は仮の名前。中身は毎回調べて書く）

dialogue（interview はこの前に地の文のリード文が入る）:

```markdown
<!-- EYECATCH images/5-eyecatch.png -->
**{質問役}**: 〇〇って、AとB、どっちにしてますか？わたしはずっとA派で。

**{解説役}**: Aもいいですよね。でもBにすると、△△が長く続くんです。

**{質問役}**: えっ、△△まで変わるんですか！

## Bだと、なぜ△△が続くのか

![AとBの違いの図](images/5-fig1.png)

**{解説役}**: ここでは、AとBで何が違うのかを見ていきますね。（以下、出典つきの説明）

:::point{title="Bにするときのコツ"}
- 〇〇する量は少しだけ
- 〇〇したてのうちに
:::
```

地の文（essay。story は最初の段落が例え話の場面になる）:

```markdown
<!-- EYECATCH images/5-eyecatch.png -->
〇〇は、AとBのどちらにしていますか？ずっとA派という人も多いと思います。

じつはBにすると、△△が長く続きます。

## Bだと、なぜ△△が続くのか

![AとBの違いの図](images/5-fig1.png)

ここでは、AとBで何が違うのかを見ていきます。（以下、出典つきの説明）
```

## 5. 画像（2枚以上・省かない）

`media.config.json` の `image_mode` で動きが変わる。どちらでも同じコマンドを使い、記事に書くパスも同じ。

- `manual`（無料）: 画像は作らず、**指示文**を `images/{id}-{name}.prompt.txt` に保存する。人が下書き.html から指示文をコピーし、ChatGPT・Canva などで画像にする
- `gemini`: Gemini で画像を作り `images/{id}-{name}.png` に保存する（支払いの登録が要る）

```bash
python scripts/gen_image.py {id} eyecatch "プロンプト" --aspect 16:9   # note の見出し画像
python scripts/gen_image.py {id} fig1 "プロンプト" --aspect 4:3       # 本文の図解
```

- 指示文はそれだけで画像が作れるように書く（何を・どんな構図で・画像の見た目・入れる文字）。manual のときは人が読んで別の道具に貼るので、日本語でよい
- 出てきたパス（`images/{id}-{name}.png`）だけを記事に書く。自分でパスを作らない・ネットの画像を使わない。失敗したら止まるので、直してやり直す
- 画像はネットに置かない（下書き.html に埋め込んで、文章と一緒に note へ貼るため）
- 見た目: {画像の見た目}。指示文に「避けること: {避けること}」も必ず書く（書かないと、線画を頼んでも水彩になることがあった）
- {見本} があれば、manual の指示文の最後に「タッチの見本: {見本}（ChatGPT なら、この HP か画像のスクリーンショットを添付して、色とタッチをそろえる）」と1行足す
- 画像の中の文字は日本語で短く（3〜8字を2〜3か所まで。長い文は崩れる）
- 実在の商品パッケージ・ロゴ・人の顔を描かせない（本物と違うものが出るため）

## 6. 事実確認（4段階・全部やる）

1. **数字・言い切り**: 記事中の数字と「〜です」と言い切った一般論が、quotes の文と合っているか
2. **会社・商品**: 会社・商品について書いたことが、全部 facts/確かめた事実.md か商品ページの引用にあるか
3. **URL**: 記事中の全 URL が生きているか（`python scripts/web.py status URL` が 200）
4. **商品リンク**: 商品へのリンクが {商品} の url のどれかか

1つでも NG なら直してから次へ。

## 7. 提出前の検証（3段階）

1. **機械チェック**: `python scripts/check_article.py work/article_{id}.md` が OK になるまで直す
2. **事実確認の結果**: 上の4段階が全部 ✅
3. **保存して確かめる**:

```bash
python scripts/db.py save-draft {id} work/article_{id}.md "タイトル" work/notes_{id}.json
python scripts/check_article.py --id {id}
```

全部通るまで、レビュー依頼（＝報告）を出さない。3回直しても通らなければ、通らない理由を報告に書いて返す。

## タイトル（article_title）

- 読者の疑問か、やってみたくなる一言。28字以内
- 例: 「〇〇はBにすると、△△が続く話」
- 「徹底解説」「完全ガイド」「〜の全て」は使わない

## 編集長への報告

```
記事ID: {id}
タイトル: {title}
文字数: {本文の字数}
出典: {sources の件数}件（信頼できる出典 {n}件）
画像: 見出し1枚 / 図解{n}枚（全部ファイルか指示文あり）
事実確認: ✅ 全部 / ❌ {項目}
  - 数字・言い切り: ✅/❌
  - 会社・商品: ✅/❌
  - URL: ✅/❌
  - 商品リンク: ✅/❌
機械チェック: ✅ OK / ❌ {E番号}
→ レビュアーの審査が必要
```

## 自己診断（quality_check に書く）

- ✅/❌ {テイスト}の形どおり（話者あり: 始まり方が合い、話者が逆転していない／地の文: `**名前**:` を使わず、1段落4文まで）
- ✅/❌ 会社・商品のことは確かめた事実だけ（interview・documentary の発言と場面は {取材メモ} だけ。story の場面は例え話と分かる）
- ✅/❌ sources 3件以上・信頼できる出典1件以上・数字に全部 quote
- ✅/❌ 画像2枚以上（gen_image.py が出した images/ のパス。manual なら指示文あり）
- ✅/❌ check_article が OK
- ✅/❌ {言えないこと}・相対の時制なし

## ルールを足すとき（孤立ルールを作らない）

新しい「必ず〜する」を足すときは、次の全部に同時に入れる。

1. この手順の流れ（何番で守るか）
2. `scripts/check_article.py`（E番号で機械的に見つけられるように）
3. レビュアーのチェックリスト（`media-article-reviewer`）
